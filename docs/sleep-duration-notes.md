# 睡眠时长口径说明 · 2026-10-10 虚高 14 小时事件复盘

> 版本：1.2.0-cn.5（时间窗收口）→ cn.6（对齐 App「真睡着」口径）｜ 修复文件：`custom_components/mi_fitness_cn/coordinator.py`
> 关联：上午提交 `29297ce`（睡眠续发尾巴修复）只修了分段 timeline，本篇记录后续发现的合计虚高问题、两次修复，以及最终与小米 App 的口径对齐决策。

## TL;DR

- **最终口径（cn.6）**：睡眠时长 = 分段 timeline 里扣掉「醒」态的**真睡着分钟数** —— 与小米 App 头条完全一致（实测当日两边都是 10h30m）。
- **卡片（freeUI SleepCard / MiBandCard）不需要改**：两张卡的大字总时长读的就是 `sleep_duration` 实体的 state（今天页）和 `history_14d[].duration`（历史页），深/浅睡读集成属性——集成改对，卡片自动跟着对。
- 事件：当日合计一度显示 14h03m，成因是夜里记录的自报 `duration=630` 超出时间窗（452）且被入库规则焊死，`843 = 630 + 213(午睡)` 直接相加所致。

## 1. 事件：当日合计 14h03m 是怎么算出来的

2026-10-10 用户夜里 22:13 睡、早晨 05:45 起，中午 12:50-16:24 午睡。卡片当日合计显示 14h03m（843 分钟），与 App 一致，但真实体感只有 10 个多小时。

从集成存储（`.storage/mi_fitness_cn_watermarks_<entry_id>`）拉出当日两条 `sleep_records`：

| 记录 | 真实时间窗 | 自报 duration | 自报 deep / light |
|---|---|---|---|
| 夜里 10-09 22:13 → 10-10 05:45 | 452 分钟（7h32m） | **630 分钟（虚高 178 分钟）** | 143 / 487 |
| 午睡 10-10 12:50 → 16:24 | 214 分钟（3h34m） | 213 分钟 ✓ | 51 / 162 |
| **合计** | 666 分钟 | **843 分钟 = 14h03m** | 194 = 3h14m / 649 = 10h49m |

App 头条当时显示的 14h03m、深睡 3h14m、浅睡 10h49m 与上表逐项吻合——**App 拿的也是这套自报数据，当时 App 自己也是虚的**（用户实测后 App 把头条修正成了 10h30m，见 §3）。

### 成因链

1. 夜里会话在早晨被手环撑大（赖床时段被算进会话），小米自报 `duration=630`（22:13+630min = 08:43，超出真实醒来时刻近 3 小时）。
2. 小米随后重发了纠正数据（wakeup=05:45、分段 25 条都正确），但入库规则 `同 bedtime 取更长的 duration`（`_upsert_sleep_record`）把变小了的纠正值挡在门外——**分段和 wakeup 被吸收了，duration 永远停在 630**。
3. 浅睡 487 是小米的「凑余数桶」（630 − deep 143 − rem 0），跟着撑大的 duration 一起虚高。
4. 当日合计 `_rebuild_sleep_views` 把两条记录的自报 duration 直接相加 → 843。

> 上午的「续发尾巴切切」（`_split_stray_sleep_tails`）解决的是另一件事：分段 timeline 被续发污染、wakeup 被撑远。它刻意不动「小米自报口径」的 duration/深浅——本事件证明自报数值本身也会被污染且被焊死，这就是后续要补的口子。

> ⚠️ 巧合预警：夜里那条记录的脏 duration 恰好是 630 分钟，而当日「真睡着」合计也是 630 分钟（§3），纯属数字撞车，翻旧存储时别被误导。

## 2. 修复一：`_clamp_sleep_summary`（cn.5，时间窗收口）

在 `_rebuild_sleep_views()` 每次重建视图、合计之前逐条执行：

- **窗口收口**：`duration > (wakeup − bedtime)` 时把 duration 截到时间窗。睡眠不可能超过躺在床上的时间。
- **浅睡兜余**：deep + light + rem 超过截后 duration 时，差额从浅睡里扣（浅睡本来就是小米的余数桶）。
- **只缩不涨**：干净的记录分毫不动；在库的脏值不用迁移，读路径每次自愈。

顺带修正睡眠效率：分母从「首尾跨度」（会把午睡前的 8 小时清醒算进在床时间；10-09 曾算出 105%）改为**各会话窗口之和**；分子改用分段扣掉「醒」态的真睡着分钟。

效果：当日 843 → 665 分钟（11h05m，在床口径），历史夜 513→468、501→477 顺带自愈。

## 3. 修复二：对齐 App「真睡着」口径（cn.6，最终状态）

App 把头条修正后显示 **10h30m**，用存储分段可以逐分钟对上：

```
夜里真睡着 = 452 − 35(夜醒 4 段: 22:50-22:54, 02:08-02:33, 04:43-04:46, 05:29-05:32) = 417
午睡真睡着 = 213(小米自报已扣掉 14:17-14:18 的 1 分钟醒)
合计       = 417 + 213 = 630 分钟 = 10h30m  ← App 头条,与 cn.6 集成分毫不差
```

历史夜同样符合该规律（App 头条 ≈ 分段扣醒态），故决定集成整体切到该口径：`_clamp_sleep_summary` 升级为 `_normalize_sleep_summary`——

- **有分段**：`duration = 分段非醒态合计`（真睡着，App 口径）；
- **无分段**（整段浅睡兜底的小睡等）：退回自报 duration，但仍按时间窗收口；
- 深/浅/REM 收进时长内：深睡超了截深睡，差额从浅睡（余数桶）里扣；
- 在床口径的信息不丢：入睡/醒来实体照旧，在床时长 = 醒来 − 入睡 − 会话间隙，效率 95% = 真睡着 630 / 在床 666。

### 实测验证（cn.6 部署重启后，从 recorder 库读实体值）

| 实体 | 事件前（脏） | cn.5（在床口径） | **cn.6（真睡着，= App）** |
|---|---|---|---|
| sleep_duration | 843（14h03m） | 665（11h05m） | **630（10h30m）** |
| deep_sleep_duration | 194（3h14m） | 194 | **194 ✓** |
| light_sleep_duration | 649（10h49m） | 471（7h51m） | **436（7h16m）** |
| sleep_efficiency | 77 | 95 | 95 |
| sleep_quality | 69 | 69 | 69 ✓ |

深睡 194 + 浅睡 436 = 630，与时长自洽；App 当日深睡 3:14、总时长 10:30 与集成逐项一致。

### 卡片侧结论（freeUI）

- `src/widgets/sleep/SleepCard.tsx`：今天页大字总时长 = `stateToMinutes(sleep_duration 实体)`，历史页 = `history_14d[].duration`，深/浅睡 = 集成属性；
- `src/widgets/miband/MiBandCard.tsx`：同样读 `sleep_duration` 实体 + `history_14d`；
- **均不自行计算时长 → 集成切口径后卡片自动正确，无需改卡片、无需重新构建 freeUI。**
